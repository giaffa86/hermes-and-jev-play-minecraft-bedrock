## Source code (authoritative for behaviour)

| Path | What it defines |
|---|---|
| `construction.mjs`, `bedrock-construction.mjs`, `construction-api.mjs`, `structures/` | Validated construction blueprints, bounded persistent executor and HTTP routes. |
| `bedrock-adapter.mjs` | The Bedrock protocol client: perception (`_refreshNearby`), actions (`player_auth_input`, `block_action`, `item_stack_request`, `click_block`), tool selection, mining, digging, containers, trading and trader levelling, chat capture (`text` id 9 → `chatInbox`) and chat **output** (`sendChat` → `text`/`chat` packet), `follow_player`, human players in range (`observe().humans`, `_nearbyHumanPlayers`), who the bot itself is (`observe().self`: the auth `username` and the gamertag learned from the chat echo) and the valuable-ore opportunity scan (`observe().ores`, the `mine_<ore>` options outside the fixed mining list). Since M6.4 it also offers the **copper tier** (`craft_copper_pickaxe|sword|axe|hoe|shovel` and the four armour pieces), gated by `_craftable(name)` — the recipe is known *and* `_hasMaterials` passes over the slots or the aggregate `inventory` — and only while the craft is an upgrade (no tool of that kind at harvest rank ≥ `TOOL_HARVEST_RANK.copper` = 2, no piece worn or carried). Since M3c it also owns the **deposit policy**: `_isKeptItem`/`_depositableItems` (tools, armour, buckets, seeds, torches and portable stations, `DEPOSIT_KEEP_RESERVE = 16` of every food stack), `_depositTargetFor` (a container that already holds the item scores `+100000`, then the distance, cached-only when the moment must stay cheap), the `dump_inventory` action (`DEPOSIT_MAX_STACKS = 8`, keeps the reserve, returns what it moved) and `observe().deposit` (`{items, total, target, at}`). `_depositStackInto` is shared by `deposit_<item>` and the dump, and accumulates the container contents across the stacks of one dump instead of recomposing them from the open-window slot mirror. |
| `remembered-resource-sites.mjs` | Historical resource-site ranking and navigation-only sourcing shared by crafting and construction; live gather keys required. |
| `bedrock-trading.mjs` | Pure trading economy rules: profession mapping, item value classification, cheapest-trade picker for levelling. |
| `bedrock-bees.mjs` | Pure Bedrock apiculture rules: known honey levels, campfire smoke safety, hive protection and supported feeding flowers. |
| `bedrock-fishing.mjs` | Pure fishing rules: fish classification, water-block detection, shore geometry, bite timing. |
| `bedrock-world.mjs` | Registry + Prismarine v9 decoder, `findBlocks`/`blockAt`, `requestAround` (subchunk requests). |
| `bedrock-harness.mjs` | HTTP API (`/observe`, `/options`, `/act`, `/plan`, `/say`, `/survival`) and the Survival Governor filter; owns the `WorldMemory` (load, periodic flush, close). |
| `world-memory.mjs` | Persistent **world memory** service: landmark/container records, `known/stale/invalid` status, spatial queries; storage-agnostic. Since 2026-10-07 it also holds the **told facts** (M10): `TOLD_SOURCE`, the permanent named places (`tellPlace`, `correctToldPlace`, `placesForName`, `resolvePlace`, `forgetPlace`) and the partial claims on a chest's content (`claimToldContents`, `claimsFor`, `whereToFind`) — [wiki/memory](wiki/memory.md#told-facts-what-a-human-said). |
| `memory-chat.mjs` | Pure **told-facts sentence reader** (M10): `toldIntentFromText(text, {sender, names})` → the four memory operations (remember / consult / correct / forget), the movement order to a remembered name, or `null` when the message is not a memory fact. Token-level rewriting (`analyze`/`drop`), coordinates only with an explicit marker (`isWorldPosition`, `coordsFromText`), the sender's live position for a deictic, the container/item/count phrase, and the `CLARIFY` reasons (`no_name`, `no_position`, `no_marker`, `no_sender_position`). Five languages, no network, no model. |
| `sqlite-memory.mjs` | SQLite repository (`node:sqlite`, WAL, chunk index) — default memory backend. |
| `memory-store.mjs` | JSON repository (same interface) — fallback / tests. |
| `exploration.mjs` | Deterministic exploration M1 planner: biome target resolution, expanding-square/spiral over unexplored chunks, biome detection, report. |
| `explore.mjs` | Exploration M1 driver: loop planner (`GET /explore`) → `goto_waypoint` until FOUND. |
| `bedrock-lifecycle.mjs` | Disconnect/teardown lifecycle. |
| `tools/respawn-capture.mjs` | Diagnostic MITM relay (bedrock-protocol `Relay`) that records a vanilla client's death→respawn packet sequence to `runs/` (git-ignored). |
| `controller.mjs` | The planner/controller loop (incl. the human chat command channel: `CHAT_ALLOWLIST` → Hermes → `/plan`, with the multi-trigger `CHAT_PREFIXES` (`@bot` plus the bot's own name), the **chat questions** M6 (`resolveQuestion`: regex fast path, then System One over a closed intent list — answer composed from `observe()`, no goal) and the proactive greeting `maybeGreetHumans`: a human nearby is told the order syntax), the **natural-chat helper** `saySmart` (M7: the single entry point for `question`/`unrouted`/`smalltalk`/`ack`/`outcome`, which tries `composeChatReply` and falls back to the deterministic text, logging one `chat_llm` line with `via:'llm'|'fallback'`) and the **persistent session loop** (`SESSION=on`): goal → run → IDLE → next goal, with cross-session resume (`RESUME`), no reconnect; since 2026-10-06 a human order arriving mid-goal **suspends** the running goal and runs as a child (`human_preempt`), handing the parent back revalidated (`goal_resumed`/`goal_resume_satisfied`) — [goal-stack](wiki/goal-stack.md)). |
| `human-replies.mjs` | Pure chat-channel helpers: trigger normalisation/matching/derivation (`normalizePrefixes`, `matchChatPrefix`, `selfPrefixes` for the bot's own name — `observe().self` —, `DEFAULT_CHAT_PREFIX`) and the ack/outcome rendering (`orderAck`, `orderOutcome`, `renderReply`, `isSelfTriggering`). Since M7.2 every template comes from `chat-i18n.mjs` (`t(lang, …)`) and takes `lang`, so the deterministic channel speaks `CHAT_LANG` with no key. |
| `human-greeting.mjs` | Pure **proactive greeting** policy (`planGreetings`, `renderGreeting`, `formatPrefixes`): humans in range + allowlist + already-greeted state → the messages to send this step (cooldown per gamertag, zero greetings when the allowlist is empty, every configured trigger listed via `{prefixes}`). |
| `chat-i18n.mjs` | The chat **catalogue API** (M7.2): `MESSAGES` (assembled by importing the five per-language files below), `t(lang, key, vars)` (a template when `vars` is absent, interpolated otherwise — a placeholder without a value stays visible), `listAnd` for the language conjunction, `LANGS`/`DEFAULT_LANG`/`LANG_NAMES`/`LANG_NATIVE_NAMES`, and the `CHAT_LANG` resolution (`chatLangConfig`, `normalizeLang`, `isSupportedLang`, region codes tolerated, unknown value → default + one startup warning). Every sentence the bot composes by itself is looked up here and nowhere else: ack/outcome (`human-replies.mjs`), question answers and goal labels (`human-questions.mjs`), greeting (`human-greeting.mjs`), refusals, the planner fallbacks and the `chore.*`/`need.*` labels. |
| `chat-lang/{lang}.mjs` | The chat catalogue **content**, one module per language (`it`, `en`, `fr`, `es`, `de`), each `export default Object.freeze({…})` with the same flat dotted keys and the same `{placeholders}`. `chat-lang/it.mjs` is the reference and carries the section comments (which group of keys belongs to which renderer); the tests (`tests/chat-i18n.test.mjs`) enforce key and placeholder parity, so a translation lives in exactly one file. |
| `chat-narration.mjs` | Pure **autonomy narration** (M8): `narrateGoal(plan, {lang})` turns the plan of a goal nobody asked for into one sentence from the catalogue (`autonomy_narration` + `narrate.<choreId>`, or `narrate_need` + `need.<id>` for a governor need); `narrateChore`/`narrateNeed` compose it and `targetWord` names the concrete item (`item.<id>`) or at least its family (`kind.log`, `kind.ore`, `kind.crop`, …), so a raw id never reaches the chat. Pure and deterministic: the sentence is fixed before the optional LLM sees it. |
| `human-questions.mjs` | Pure **chat question catalogue** (M6): the seven intents (`q_position`, `q_health`, `q_armor`, `q_activity`, `q_inventory`, `q_time`, `q_identity`) with their regex fast path, the closed option list for System One (`intentCriteria`, sentinel `q_none`), the mapping back (`intentFromChoice`) and the answer bodies composed from `observe()` (`answerIntent`, `clockFromTicks`, `renderAnswer`, `DEFAULT_ANSWER_TEMPLATE`). A question that names an item is answered about that item (`ITEM_WORDS`, `matchItemWord`) and, since M6.4, about *that material* (`MATERIAL_WORDS`, `matchMaterial`, `MATERIAL_KINDS`: `bronzo`/`bronze` read as copper, because vanilla Minecraft has no bronze — The Copper Age added the copper tier) with `no, non ne ho; ho: …` instead of a flat refusal when the material is missing. `q_armor` answers the **worn** slots (`armorAnswer`, `observe().armor`) and `healthAnswer` leads with hearts. It also owns the **question guard** `looksLikeQuestion` (M6.1: explicit `?`/`¿` or an interrogative first word, evaluated on the raw text), the **small-talk classifier** `looksLikeSmallTalk`/`SMALL_TALK` (M7: an **exact** closed match on the normalised message, so `grazie` is small talk but `grazie prendi la legna` stays an order) and the refusal lines (`renderUnrouted`, `UNROUTED_TEMPLATE`: "non ho capito la domanda", with the way back to the order syntax; `renderNoArmor` for an equip order with nothing to wear). Since **M7.1** it also owns the Italian chat vocabulary for the structured goals: `CHORE_LABELS`/`NEED_LABELS` + `planPhrase` turn a village chore, a survival need, `wear_armor`, a loot recovery or an `opportunity:`/`curriculum:` plan into the sentence `activityAnswer` sends, so an autonomous goal never reaches chat with its English knowledge-base objective (an order keeps its own `objective`, already written in the human's language). It never writes a fact it does not have. |
| `chat-intent.mjs` | The **chat question router**: regex first, then System One (Jev) over the closed intent list (`classifyQuestionIntent`, `resolveQuestionIntent`, `DEFAULT_INTENT_TIMEOUT_MS` 4000, `DEFAULT_INTENT_MIN_P` 0.4). Its result carries an `action` (M6.1): `answer`, `order` (not question-shaped, or `q_none` from a working model — `q_none` is a verdict, not a failure) or `unrouted` (question-shaped and the router is off/without key, times out, errors, is unparsable or lands below the probability floor). A failure never becomes an order, and a non-question-shaped message never costs a model call (the pre-filter). |
| `chat-llm.mjs` | The **natural-chat layer** (M7): an OpenAI-compatible `/chat/completions` client (DeepSeek default) that *rephrases* the deterministic chat reply in the sender's language and first person. `chatLlmConfig`/`chatLlmKey` gate it on `DEEPSEEK_API_KEY`/`CHAT_LLM_API_KEY` (`CHAT_LLM=off` overrides), `compactChatFacts` builds the only facts the model may use from `observe()` (+ the plan), `buildChatMessages` writes the system prompt (same language, first person, one line, facts only, never start with a trigger) and `composeChatReply` returns `{text, model, ms, cost}` or throws with a `code` (`no_key`, `timeout`, `transport`, `http_*`, `empty`, `self_trigger`). `createChatMemory` is the bounded per-sender history (6 turns, 8 senders, in RAM). The model never chooses an action and never creates a goal: every failure is the deterministic template. |
| `system-one.mjs` | System One (Jev) transport shared by the action decision and the chat question router: `systemOneConfig` (TypeSafe when `TYPESAFE_API_KEY` is set, otherwise the OpenRouter decisions endpoint) and `systemOneDecide` (`{state, questions}` → `{answers, model, provider, usage, ms}`). Failures carry a `code` (`no_key`, `http`, `api`, `unparsable`) so the router can report *why* it could not decide. |
| `goal-manager.mjs` | Pure **Goal Manager** (Agent Core, M1): goal model, sources/priorities, `PENDING/RUNNING/SUSPENDED/COMPLETED/FAILED` transitions, preemption, snapshot/restore, cross-session resume, persistence via a repository (`kind: 'goal'`). Since 2026-10-06 it also exposes the parent chain — `ancestors(id)`/`depth(id)` (nearest-first, orphan- and cycle-safe) — so a human order can nest as a child of the suspended goal (`MAX_GOAL_DEPTH`); see [goal-stack](wiki/goal-stack.md). |
| `idle-goals.mjs` | Pure **idle autonomy** (M3): maps survival needs to ranked candidate goals (+`nextIdleGoal` cooldown) and the deterministic `isNeedResolved` success predicate. |
| `village-labor.mjs` | Pure **village labor** (M3b): derives the bounded chores the harness is already offering (`harvest_crops`, `store_harvest`, `shear_sheep`, `milk_cows`, `collect_honey`, `tend_animals`, `plant_crops`, `go_fishing`, `chop_wood`, `gather_stone`, `mine_ore`) from `observe()` and ranks them; `offeredHas`/`offeredMatches` make `GET /options` the arbiter, and `isChoreResolved`/`choreGain`/`villageSnapshot` verify a **state delta** (items gained, a seed spent, a baby born), never an absolute count. `targetOf` reports what a chore is working on (`{kind, item}`) for the M8 narration. Since M3c `storableStack` reads the harness census (`observe().deposit.items`) first and only falls back to its own family filter, and `store_harvest` also accepts the generalised `dump_inventory`. No LLM. |
| `world-events.mjs` | Pure **world-event detection** (M2): transition-based `detectEvents(prev, curr)` → `PLAYER_DIED`, `LOW_HEALTH`, `HOSTILE_AMBUSH` and `VALUABLE_ORE_SEEN` (a newly seen ore within 24 blocks), each with a `dedupKey`. |
| `emergency-goals.mjs` | Pure **emergency mapping** (M2): `emergencyGoalFor(event, …)` maps events to preempting `EMERGENCY` goals (`PLAYER_DIED → recover_loot`), with cooldown/dedup. |
| `ore-value.mjs` | Pure **ore/item value table** (`ORE_VALUES`, `ITEM_VALUES`): the deterministic answer to "is this vein worth a detour?" — thresholds for the event floor, the option-priority lift and the opportunity gate. |
| `opportunity-goals.mjs` | Pure **opportunity mapping** (curiosity): `evaluateOpportunity(event, …)` / `opportunityGoalFor(event, …)` turn a `VALUABLE_ORE_SEEN` event into a suspending `OPPORTUNITY` goal (relative-value gate, cooldown/dedup, one level, never over a chat order). |
| `controller-decisions.mjs` | Pure decision helpers (ranking, anti-loop, cap, diagnostics), incl. the **valuable-ore tier 4.5** for gold-and-above ore and the equip-order classifier `isEquipOrder` (M6.3: an equip verb *plus* an armor noun — `equipaggiati`/`mettiti`/`indossa`/`wear`/`put on`, so `mettiti a lavorare` stays an order). Since **M9** it also owns the inventory-order detectors (`isDropOrder`/`isCollectOrder`, `orderItem`, `dropCountFromText`) and their success criteria (`inventoryMatchingToken`, `matchesItemToken`, `tokenInventoryTotal`, `dropFulfilled`, `collectFulfilled`). |
| `survival/resolver.mjs` | The survival-layer resolver: which option the governor allows, the emergency restriction of `/options` and `humanOrderProtectedKeys(plan)` (M9) — the keys an open human order keeps even under the emergency filter (`follow_player`/`seek_player`, `drop_item`, `collect_drop`). |
| `survival/` | Survival Intelligence Layer (governor, resolver, verifier, progression, ...). |
| `knowledge/` | `survival-rules.json`, `progression.json`. |
| `skills/gameplay/` | Declarative gameplay skills. |
| `harness.mjs` | The Java Edition "toy" harness (flying-squid + mineflayer). |

| `construction-design.mjs` / `construction-planning.mjs` | Model-owned architectural geometry, compiler contracts and read-only planner repair; no aesthetic fallback. |
