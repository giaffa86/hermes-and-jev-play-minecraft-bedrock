# Agent notes

Compact guidance for working in this repo.

## Privacy rules — never push personal data to GitHub

This repository is **public**. Before any `git push`:

- Never commit or push personal data: real gamertags or account emails, Microsoft/Xbox credentials or token caches (`nmp-cache/`, `auth.json`), API keys (`.env*`), SSH key paths or key files, xuid/account IDs, allowlists, chat logs.
- Use placeholders in examples and docs (`<gamertag_or_email>`, `<ssh-key>`, `<api-key>`), never real values.
- `.env`, `.private/`, `runs/`, `nmp-cache/`, `auth.json` are gitignored — never `git add -f` them.
- Audit before pushing: `git log -p origin/main..HEAD` plus a `git grep` for the patterns above. If a value already sits in unpushed commits, rewrite the history (scrub it) instead of pushing it or adding a "remove secret" commit.
- If unsure whether something is personal, ask the user before pushing.

## What this is

A minimal reproduction of the rmalde/minecraft-agent planner/controller split: **Hermes** plans milestones, **Jev** (or Hermes) picks one bounded action at a time, and a **Mineflayer + flying-squid harness** executes it. No screenshots, no keypresses, no generated code.

## Project shape

- ESM Node project; no build, no formatter config. CI is `.github/workflows/ci.yml`
  (`ci` workflow on GitHub, the only remote), mirrored in `.gitea/workflows/ci.yml`

- `survival/` is the deterministic Survival Intelligence Layer (governor, skill resolver, verifier, progression); `knowledge/*.json` holds rules and the milestone graph; `skills/gameplay/**` holds declarative gameplay skills (distinct from the Hermes `SKILL.md`) — including `skills/gameplay/redstone/` for the circuit milestones; `circuits/*.json` holds declarative redstone circuit blueprints built by `build_circuit_<id>` (validated by `circuits.mjs`, results in `runs/<run>/circuits.jsonl`). See `docs/raw/SURVIVAL-INTELLIGENCE.md` and `docs/wiki/redstone.md`.
- `docs/` is an **LLM wiki** (English). Read `docs/index.md` first, then the relevant `docs/wiki/*` pages; raw sources live in `docs/raw/` and `BEDROCK.md` at the root. Conventions and workflows in `docs/llm-wiki.md`. Keep all docs in English.
- Tests: `node --test tests/*.test.mjs` (no server required).
- Wiki lint: `npm run wiki:lint` (strict: `npm run wiki:lint:strict`). The git
  hooks are versioned in `tools/hooks/` and activated with

  `pre-push` blocks on warnings too (including the public-repo privacy scan) and

## Run the demo

Two terminals required:

```bash
# Terminal 1 — boot the server. First run generates the world, ~25 s.
RUN_ID=demo node harness.mjs
# Wait for: "harness api on 3077"

# Terminal 2 — Hermes plans, Jev acts
export OPENROUTER_API_KEY=sk-or-...
RUN_ID=demo WAYPOINT='{"x":380,"z":16}' TARGETS='{"dirt":4}' MAX_STEPS=14 node controller.mjs
```

Result: `GOAL MET after N actions`. Logs land in `runs/demo/controller.jsonl` and `runs/demo/events.jsonl`.

Use `CONTROLLER=hermes` if you lack an OpenRouter key; it is slower and costlier.

## Important env vars

- `RUN_ID` — output directory under `runs/` (default `run`).
- `HARNESS` — harness URL (default `http://127.0.0.1:3077`).
- `WAYPOINT` — JSON `{"x":N,"z":N}`; omit for no waypoint.
- `TARGETS` — JSON `{"dirt":4}` (default `{dirt:4}`).
- `MAX_STEPS` — action budget (default `20`).
- `MAX_GOAL_DEPTH` — depth of the `parentGoal` chain (`goalManager.depth`) above which a human order arriving mid-goal goes back to *reorienting* the running goal instead of nesting as a child (default `3`); a depth-capped preemption logs `human_order_override`. See `docs/wiki/goal-stack.md`.
- `REPLAN_EVERY` — replan every N actions (default `8`).
- `CONTROLLER` — `jev` (default) or `hermes`.
- `JEV_MODEL` — default `typesafe/jev-1.13`.
- `HERMES_TIMEOUT_MS` — planner timeout before falling back to a static plan (default `180000`).
- `MAX_OPTIONS` — cap on the options passed to Jev (default `12`, `0` disables).
- `ANTI_LOOP_THRESHOLD` / `ANTI_LOOP_COOLDOWN` — stagnant-action replan threshold and cooldown (default `3` / `3`).
- `HARNESS_BUSY_MAX_WAIT_MS` / `HARNESS_BUSY_POLL_MS` — how long the controller waits for the harness lock (a `busy` answer) and how often it retries the same action (default `90000` / `2000`); `busy` never consumes a step.
- `HARNESS_ACTION_TIMEOUT_MS` — ceiling on a single harness action (default `180000`): on expiry the action resolves `{ok:false, error:'action_timeout'}` and the `busy` lock is released even if the body is still pending (a death mid-action used to wedge the whole API).
- `MC_PORT` / `API_PORT` — defaults `25599` / `3077`.
- `OPENROUTER_API_KEY` — required for `CONTROLLER=jev`.
- `CURRICULUM` — optional milestone (`first_night`, `enter_nether`, `redstone_automation`, `bucket`, `water_travel`, `nether_cross_lava`, or the composite goal `prepare_for_nether`): the progression engine picks missing prerequisites itself; Hermes is only a fallback. A **composite** goal (`goals` in `knowledge/progression.json` naming an array of milestones, R5) expands through `milestoneChain` into the missing closure in dependency order, the plan carries the whole chain in `steps[]` and the goal closes only when **every** target is satisfied.
- `PROGRESSION_GOAL` — optional harness-side goal for the diagnostic `GET /survival` route.
- `CHAT_ALLOWLIST` — comma-separated gamertags/xuids allowed to order the bot via in-game chat (enables the `@bot` command channel; see `docs/wiki/human-command.md`).
- `CHAT_PREFIXES` — triggers accepted for an order, comma or space separated (e.g. `@bot,@hermes`; default `@bot`). The longest match wins, so `@bot1` is not `@bot`; several triggers let one bot answer to both a generic word and its own name, and are the prerequisite for running several bots on the same server (each needs its own distinct triggers).
- `CHAT_PREFIX` — legacy single trigger (default `@bot`); summed into `CHAT_PREFIXES`.
- `CHAT_SELF_NAME` — `on`/`off` (default `on`): the bot also answers to **its own name** — `@<BEDROCK_USERNAME>` and the gamertag the server attributes to it (learned from the chat echo, exposed as `observe().self.name`). `on` by default because it is the most natural way to address a bot, and because several bots on one server can then each be called by name without sharing a trigger; `off` keeps only `CHAT_PREFIXES`.
- `CHAT_CONTROL` — `on`/`off` (default `on` when `CHAT_ALLOWLIST` is set).
- `CHAT_GREET` / `CHAT_GREET_RANGE` / `CHAT_GREET_COOLDOWN_MS` / `CHAT_GREET_TEMPLATE` — proactive greeting: a nearby trusted human is told the order syntax via `POST /say` (default on when the channel is open, range `24`, cooldown `600000` ms); the template lists every configured trigger (`{prefixes}`).
- `CHAT_REPLY` — `on`/`off` for the order lifecycle replies (ack + outcome, default on when the channel is open; `CHAT_REPLY_MAX_LENGTH` default `180`).
- `CHAT_MAX_AGE_MS` — an order older than this (default `300000`) is dropped as stale (`chat_stale`) so a restarted controller does not replay the harness inbox.
- `CHAT_CLARIFY` — `on`/`off` (default `on`, R2): an order that asks for a destination and carries none, when no source can resolve it, does **not** become a goal — the bot asks **one** question and holds the order in the harness inbox until the same sender answers. The gate is pure (`human-clarify.mjs`, `orderGaps`), runs on the plan `humanCommandPlan` decided, and only asks what the repo cannot already resolve (a destination in the plan, a follow verb / «qui» / explicit coordinates, an activity after «vai a …», a place the world memory knows, an object a partitive introduces); with the place memory down the gate stays open. The pending record is written by `POST /chat/ask` (the only writer: `askChat`) *before* the question is spoken, is stamped onto the sender's next addressed message as a one-shot `clarifies`, and expires with `CHAT_ASK_TTL_MS` (default `300000`, the same window as `CHAT_MAX_AGE_MS`). A reply that is itself an order (`vai al mulino`, `fermati`) replaces the held one instead of being merged; a second gap is a typed refusal, never a second question; `off` restores the old planner fallback (see `docs/wiki/human-command.md` §R2 and `docs/wiki/reasoning-roadmap.md`).
- `CHAT_ASK_TTL_MS` — how long a pending clarification stays answerable (default `300000`); an older one is dropped and logged `chat_ask_stale` by the adapter. Used by R2 only.
- `SYSTEM_ONE_RETRY_ATTEMPTS` / `SYSTEM_ONE_RETRY_BASE_MS` / `SYSTEM_ONE_RETRY_MAX_MS` / `SYSTEM_ONE_RETRY_JITTER_MS` — the retry policy of System One decisions (defaults `4` retries after the first call, `1000`/`8000` ms backoff ceiling and `250` ms of full jitter, i.e. at most 5 calls and ~15 s of waiting). `systemOneDecideWithRetry` (`system-one.mjs`) retries **only** failures that did not carry a decision: `408`/`429`/`5xx` (including the `529 system_overloaded` and `504` that on 07/10/2026 killed the run at every decision) and network errors; a `401`/`403`, an unknown model or a `200` without `answers` fails at once. `SYSTEM_ONE_RETRY_ATTEMPTS=0` is the kill-switch. `timeoutMs` is the **total** budget, so a `CHAT_INTENT_TIMEOUT_MS=4000` question still waits 4 s at most.
- `CHAT_INTENT` — `on`/`off` for the chat **question** path (default `on` when `TYPESAFE_API_KEY` or `OPENROUTER_API_KEY` is set): a message that asks about the bot's own state is answered from `observe()` and creates no goal. `CHAT_INTENT_URL` points at an alternative decisions endpoint, `CHAT_INTENT_MODEL` picks the routing model (default `JEV_MODEL`), `CHAT_INTENT_TIMEOUT_MS` (default `4000`) bounds the wait and `CHAT_INTENT_MIN_P` (default `0.4`, `0` = argmax) is the probability floor below which the message is **refused**. The regex fast path needs no key and always runs first. **M6.1**: `looksLikeQuestion` (explicit `?`/`¿` or an interrogative first word, evaluated on the raw text) is a **pre-filter** — a message that is not question-shaped never costs a model call before its ack — and a question-shaped message the router cannot decide (no key, `off`, timeout, error, unparsable, below the floor) is answered with `renderUnrouted` ("non ho capito la domanda. Se era un ordine, scrivi \"@bot <ordine>\"."), logged as `chat_unrouted` with `reason`/`probability`/`model`/`ms`/`cost`, and **creates no goal**. `q_none` from a working model still means "it was an order".
- `CHAT_ECHO_WINDOW_MS` — window (default `15000`) used to recognise the bot's own chat coming back from the server (`chat_echo`); the server rewrites `source_name` with the real gamertag, which differs from `BEDROCK_USERNAME`.
- `TOLD_FACTS` — `on`/`off` (default `on`) for the **told facts** (M10): a human can dictate a fact about the world and the bot remembers who said it. The chat channel recognises **remember / consult / correct / forget** in five languages (`memory-chat.mjs`, deterministic, no model) plus «vai al campo di patate» as an ordinary movement order to the remembered position (`told_goto`); remembering never interrupts the running goal. A dictated place is `source: 'told'` with `toldBy`/`toldAt` and **no TTL** (`permanent`); a chest's content is a *partial claim*, never an inventory (the observed contents are kept, `contentsKnown` stays `false`, the verdict comes from the next real reading, stale after 7 days); a correction keeps identity and history, forgetting only invalidates; an ambiguous name is always asked, never resolved by distance. Write routes `POST /memory/tell/place|container|contents|forget`, read routes `GET /memory/places|where|claims`; with `off` the writes answer `403 {error:'told_facts_disabled'}`, and when `CHAT_ALLOWLIST` is set in the harness too a fact attributed to a sender outside it answers `403 {error:'told_sender_not_allowed'}` (a write with no `toldBy` is not a human order and stays possible); repeating a fact unchanged is `action: 'unchanged'` and writes nothing (see `docs/wiki/human-command.md` §M10 and `docs/raw/TOLD-FACTS.md`).
- `ORE_ALERT` / `ORE_ALERT_RANGE` / `ORE_ALERT_COOLDOWN_MS` — the **ore alert** (M11): the harness says in chat when the census finds a valuable vein. `ORE_ALERT` is the ore list (`diamond` by default, `off`/`none`/`''` = silence; `_ore`/`deepslate_` are folded away, so `diamond_ore` and `deepslate_diamond_ore` are the same core), `ORE_ALERT_RANGE` (32) bounds the distance and `ORE_ALERT_COOLDOWN_MS` (5000) spaces two alerts. One sentence per vein, once per position, never twice; the text comes from the catalogue (`ore_alert`, five languages) and is injected into the adapter by the harness (`adapter.oreAlertText`), so the adapter detects and the harness words it — no model in the loop. `observe().oreAlert` carries the last one (see `docs/wiki/human-command.md` §M11).
- `CHAT_LLM_API_KEY` / `CHAT_LLM_URL` / `CHAT_LLM_MODEL` / `CHAT_LLM_TIMEOUT_MS` / `CHAT_LLM_THINKING` / `CHAT_LLM` — the **natural-chat engine** (M7): with a key the deterministic reply is *rephrased* by an OpenAI-compatible `/chat/completions` endpoint (default DeepSeek; any provider via URL/model, e.g. OpenRouter with `CHAT_LLM_MODEL=deepseek/deepseek-v3.2`). `DEEPSEEK_API_KEY` is the **legacy alias** still honoured by `chatLlmKey` (canonical name: `CHAT_LLM_API_KEY`), `CHAT_LLM=off` disables the engine, and with no key every reply is the catalogue template — the failure mode is never silence. `CHAT_LLM_THINKING` (default `off`) is the client's own switch for a model that thinks: `off` sends `{"thinking":{"type":"disabled"}}` — a reasoning model otherwise spends the whole reply budget in `reasoning_content` and the line comes back **empty** with `finish_reason: length` (measured against the DeepSeek API on 07/10/2026) — `low|high|max` send `reasoning_effort` and raise the budget (1200, 2000 for a reasoned answer), `default|auto` send nothing and let the provider decide.
- `CHAT_REASON` / `CHAT_REASON_COOLDOWN_MS` / `CHAT_REASON_MARKERS` — the **reasoned answer** (M12): a question carrying a deliberation marker (`ragiona`, `pensa`, `think`, `reason`, `réfléchis`, `piensa`, `überlege`, …; `CHAT_REASON_MARKERS` replaces the list) has the marker stripped before the dedup and the router and is answered by the M7 engine from the facts (`reasonFacts`: last six actions with their `stagnant` flag, last result, three nearest ores) with a 220-token budget, per sender at most once every `CHAT_REASON_COOLDOWN_MS` (5000). `CHAT_REASON` defaults to the state of M7 (no key = no reasoning). It changes the **reply**, never the action: no goal, no memory write; a cooldown or a failed call falls back to the catalogue, so the human always gets a sentence (see `docs/wiki/human-command.md` §M12).
- `SHIELD_THREAT_RANGE` — distance (default `8`) within which a hostile makes `raise_shield` worth offering; the shield lives in the offhand (`equip_shield`) and the use flag is `start_using_item` in `player_auth_input`.
- `STRUCTURE_RESCAN_MS` / `STRUCTURE_RADIUS` / `STRUCTURE_SURVEY_LIMIT` — structure survey throttle (default `60000` ms), radius (default `48`) and cell budget (default `20000`) of the M5/M6 detector exposed by `GET /observe.structures` (see `docs/wiki/exploration.md`).
- `OBSERVATION_DEDUPE_MS` — write-side dedupe window of the observation log (default `300000` ms): re-reading the same fact inside the window keeps the observation already stored instead of appending a row; a *different* value is always a new fact; `0` disables the filter and makes the log append-only (see `docs/wiki/memory.md`).
- `FLUID_RESCAN_MS` / `FLUID_SCAN_RADIUS` / `FLUID_SCAN_LIMIT` / `LAVA_AVOID_RANGE` — fluid census throttle (default `5000` ms), scan radius in blocks (default `24`), cell budget (default `256`) and the lava distance under which `avoid_lava` is offered (default `8`); `WADE_SPEED_FACTOR` scales the local walk speed while wading in shallow water (default `0.5`). The state is exposed by `GET /observe.fluids` (see `docs/wiki/fluids.md`).
- `DIVE_WORK_SECONDS` / `CONDUIT_RESCAN_MS` — work budget (default `3` s) the dive decision in `bedrock-dive.mjs` has to fit, together with the descent/ascent cost, into the remaining air before `_mineBlock`/`_collectDrop` are allowed under water; conduit lookup throttle (default `60000` ms). `GET /observe.dive` reports `{depth, workSeconds, waterBreathing, plan, last}` (see `docs/wiki/fluids.md` §M2).
- `REDSTONE_RESCAN_MS` — redstone census throttle (default `5000` ms); the radius and cell budget are the constants `REDSTONE_SCAN_RADIUS` (16) / `REDSTONE_SCAN_LIMIT` (24) in `bedrock-redstone.mjs`, and `REDSTONE_TRACE_LIMIT` (default `32`) bounds the observed-change trace used to *measure* a circuit's delay. `REDSTONE_TOGGLE_MIN_INTERVAL_MS` (default `500`) is the minimum interval between two toggles of the *same* input (R6: a hand-made clock is lag); the circuit builder is exempt. The state is exposed by `GET /observe.redstone` and `observe().redstone`, the safety numbers by `GET /observe.circuits.limits` (see `docs/wiki/redstone.md`).
- `NETHER_RESCAN_MS` / `NETHER_SCAN_RADIUS` / `NETHER_SCAN_LIMIT` — Nether/End awareness census throttle (default `10000` ms), scan radius (default `32` blocks) and block budget (default `64`) for portals, fire, magma and spawners; the projectile horizon and the enderman gaze tolerance are the constants `PROJECTILE_HORIZON_MS` (4000) / `PROJECTILE_RADIUS` (1.5) / `ENDERMAN_GAZE_RANGE` (16) / `ENDERMAN_GAZE_TOLERANCE_DEG` (8) in `bedrock-nether.mjs`.
- `PORTAL_APPROACH_RANGE` / `PORTAL_ENTER_TIMEOUT_MS` / `PORTAL_FRAME_RADIUS` — N1 portal actions: how close `goto_portal`/`enter_portal` stop (default `2.5` blocks), how long `enter_portal` waits for the server's dimension change (default `15000` ms) and the radius `light_portal` searches for a standing obsidian frame (default `6`). The state is exposed by `GET /observe.portals` and `observe().nether` (see `docs/wiki/nether.md`).
- `BARTER_WAIT_MS` — how long a barter waits for the piglin's drop (default `15000`); `barter_piglin` refuses a brute, a baby or a missing ingot before sending anything (see `docs/wiki/nether.md`).

## Architecture gotchas

- **An ambiguous order is a question, not a guess** (R2, `human-clarify.mjs`): the gate runs on the plan `humanCommandPlan` produced, only on the human path, and `needs_input` speaks one question and records the order in the harness inbox (`POST /chat/ask`) creating **no goal**; the sender's next **addressed** message comes back stamped once with `clarifies` and is merged with the original order — unless the reply is an order itself, which replaces it. The decoration is a *hint*: the controller keeps the last word, and a second gap is a refusal, never a second question.
- **`escort_to` is not `follow_player`**: an escort order ("guidami/accompagnami fino a X") sets `plan.escort = { from, to }` and the bot **leads**, waiting (beyond `ESCORT_MAX_GAP`, resuming within `ESCORT_RESUME_GAP`) and closing with `escort_left_behind`/`escort_lost`; `plan.follow` makes it **follow** the human instead. The two never share a field: `humanCommandPlan` sets `escort` and clears `follow`, and only degrades to follow when the order names no destination. While `goal.escort` is open and the human is out of view the controller holds (no budget spent) and releases the order after `LOST_HOLD_MAX_STEPS`.
- **A fact a human told is not a fact the bot observed** (`memory-chat.mjs` + `world-memory.mjs`, M10): a dictated place is `source: 'told'` with `toldBy`/`toldAt` and `permanent` (no TTL — time alone is not evidence a mine entrance moved), a chest's content is a *partial claim* that never becomes `contents`/`contentsKnown: true` and whose verdict (`unverified`/`confirmed`/`contradicted`) comes from the next real reading, a correction keeps identity and history, forgetting only `invalid`s the record. Ambiguity is always asked (never the nearest), an incomplete command writes nothing, repeating a fact unchanged writes nothing (`unchanged`), and the writes live in the harness behind `TOLD_FACTS` (`POST /memory/tell/place|container|contents|forget`), plus the `CHAT_ALLOWLIST` sender gate when it is set there, so chat and the future console share one path. Remember/consult/correct/forget never interrupt the running goal; only «vai al campo di patate» is an order (`told_goto`).
- **A transient provider failure is not a fatal error.** System One (Jev) can answer `529 system_overloaded` or `504` for minutes; that is a decision *not taken*, not a controller bug, so `systemOneDecideWithRetry` retries it with backoff (see `SYSTEM_ONE_RETRY_*`) before the run is allowed to die on it. What must stay fatal is a decision the provider really made (`400 unknown model`, `401/403`, a `200` without `answers`): retrying that would only repeat the same mistake. The `decision` line of `runs/<run>/controller.jsonl` carries `attempts`/`retries`, so the flakiness is visible in the ledger instead of only in the wall clock.
- **Harness owns validity.** The controller chooses only keys returned by `GET /options`. If the controller misbehaves, fix `options()` in `harness.mjs`, not the prompt.
- **The capability surface is a contract, not a document** (R7, `capability-contract.mjs`): `GET /capabilities` returns a **versioned projection** of the declarative files — `contractVersion`, `contentHash` (SHA-256 over the canonicalised content, `generatedAt` excluded), `valid` + `problems`, `counts` and the surface itself. A consumer validates it with `checkCapabilityContract(payload, { version })` (it never throws: `missing_key`, `unknown_key`, `version_mismatch`, `hash_mismatch`, `surface_invalid`), never by trusting it. The shape is frozen by `CAPABILITY_CONTRACT_KEYS`: adding a field means bumping `CAPABILITY_CONTRACT_VERSION` **and** the key list in the same commit, or `node --test tests/capability-contract.test.mjs` fails. `npm run capabilities:check` is the offline gate — wired into CI (`.github/workflows/ci.yml`) and the `pre-push` hook, never into the hook alone. MCP and any registry service stay **non-goals**: the transport is the harness's existing HTTP boundary because the contract is read-only, derived, and `knowledge/progression.json` / `skills/gameplay/**` / `circuits/*.json` remain the only source of truth.
- **The act dispatcher is order-sensitive** (`bedrock-adapter.mjs`, `_runAction`): a branch `key === 'X'` placed **after** a generic `key.startsWith('P')` with `X.startsWith(P)` is dead code, because the prefix swallows it. It already happened twice — `place_water`/`mount_boat` behind `place_`/`mount_` (live 03/10/2026) and `craft_boat`/`craft_blaze_powder`/`craft_ender_eye` behind `craft_` (live 08/10/2026, where `/options` offered the key and every attempt answered `craft_recipe_missing` before reaching its own step: the legacy name `boat` was looked up instead of the indexed `oak_boat`). Put the specific keys **before** the prefix that would match them; `tests/bedrock-dispatch-order.test.mjs` reads the chain and fails if any key is shadowed.
- **A human order suspends a running goal, it does not reorient it**: the order runs as a child goal (`parentGoal`, its own `parameters.from`) and the parent is resumed when the child closes — revalidated first, so a goal already satisfied while suspended is completed without spending an action. A *stop* order, an order from the same requester and a chain deeper than `MAX_GOAL_DEPTH` still reorient. See `docs/wiki/goal-stack.md`.
- **Deterministic survival policy lives in `knowledge/survival-rules.json`**, not in prompts. `/observe.survival` exposes the compact governor verdict; in `emergency` the harness restricts `/options` to the governor's `allowedIntents` (removing keys only, never adding, never emptying the set).
- **Gameplay skills are data, not code** (`skills/gameplay/**/*.json`): preconditions + success criteria + intents. The verifier checks harness state (`verifySkill`), never the model's opinion; results go to `runs/<run>/skills.jsonl`. A milestone whose success is a *build* has no `satisfiedWhen` shortcut: `redstone_automation` closes only through the `circuitBuilt` criterion, which reads the builder's own report and rejects a circuit that was already standing when the skill started. **Redstone circuits follow the same rule** (`circuits/*.json`): the blueprint declares steps, trigger, success checks and how its delay must be measured, `build_circuit_<id>` refuses what it cannot verify (never an empty success), a failed step rolls the site back and `teardown_circuit` removes only the cells the bot placed itself; every attempt is appended to `runs/<run>/circuits.jsonl`.
- `mine_*` options disappear once `plan.targets` are satisfied.
- `wait` is offered only when nothing else is valid.
- `collect_drop` is preferred by the controller logic whenever drops exist; drops expire.
- The harness uses `Connection: close` on HTTP responses because long pathfinding actions can outlive keep-alive sockets.
- **Every `/act` attempt is written to `runs/<run>/actions.jsonl`** (`run-ledger.mjs`): one append-only line per attempt with `ms`, `ok`, `error`, so a hand-driven run leaves the same measurable trail as a controller-driven one. `GET /stats` returns the aggregate, `shutdown()` writes `summary.json`, and `node tools/run-facts.mjs <run>` prints them for any run; `busy` refusals are counted separately and never as action time. The controller flushes a `run_end` (with `totalCost`) on SIGTERM too, so a killed run still reports its cost — a promise that had been **false** until 07/10/2026 (the handler read `stepsUsed`/`totalCost`, local to `runGoal`, and died of `ReferenceError` on every signal; the counters are now mirrored in a module-level `runProgress`).
- **The golden scenarios are the regression net of the chat/plan layer** (`tests/golden-scenarios.test.mjs`, R6): nine rows — order text + scripted world in, expected plan shape / question / typed refusal / killed-run ledger out — run the **real controller** against a scripted harness and assert on the **R3 trace**, not on the event. The seed goal is deliberately unsatisfiable (`SEED_PLAN.targets = {dirt: 99}`) so an order always lands mid-goal, and a `stopWhen` must wait one act **after** the plan is published (`actsAfterPlan`), otherwise the SIGTERM kills the controller before it adopts the plan and the trace misses the segment. When an order's outcome must stay stable, add a row there instead of a one-off test.
- **A refused action is a typed fact about the step, not a string in a log** (R4, `step-failure.mjs`): a failed action is classified into a **closed** vocabulary (`busy|timeout|transient|moved|blocked|refused|prerequisite|unknown`, built from the real strings of `bedrock-adapter.mjs`; anything unknown is `unknown` and **terminal**, never guessed retryable) and the disposition of the **step** (not the action) follows: `retry` (nothing changes: no exclusion and no plan revision), `switch` (`blocked`: only the refused key is excluded from `/options`, the alternatives stay offered, and the plan is revised so the refusal lives inside `steps[].refused`), `replan` (the step fails with `step_failed:<error>`). Attempts are counted per `activeStepId(plan)` with `MAX_STEP_ATTEMPTS = 2`; an alternative is a `siblingKeys` match on the declared intents (`optionIntents`), **recorded** in the revision but still chosen by Jev. Evidence is bounded (`refusalEvidence` drops any field whose JSON exceeds 200 characters). The typed error reaches `plan-trace.jsonl` (`kind`/`retryable`/`stepId`, `refusalsByKind`, `run-facts` printing `tipi: …`) and the skill record (`failure`). One trap: `replanReason` lives *inside* one loop iteration (`controller.mjs:2009`) — a reason produced at the end of an iteration travels in `pendingStepReplan`, declared outside the loop and consumed at the top of the next one **before** the anti-loop block.
- **Every plan adoption is written to `runs/<run>/plan-trace.jsonl`** (`plan-trace.mjs`, R3): one line per plan **segment** — opened by `adopt()` when the controller adopts a plan, closed when that plan is replaced or the run ends — carrying `source` (`hermes|deterministic|curriculum|construction`, **stamped on the plan where it is born**, never inferred), `objective`/`subgoal`/`steps`, the action keys chosen under it (`decisions[]`), the typed refusals it saw and the named closure `endedBy` (`replaced`, `human_order`, `human_order_override` for the `max_goal_depth` case, `replan:<reason>`, `goal_met[:<reason>]`, `run_end`, `goal_end`, `signal:<SIG>`). That is the *why* that used to be scattered across `log()` calls. A missed `flush()` loses nothing (`adopt()` closes an open segment and `flush()` is idempotent) and a write error is swallowed — the trace can never break a run, and there is no env flag. `node tools/run-facts.mjs <run>` prints its summary; a goal the contract closes *before* any plan is published leaves no trace, because there was no plan to trace.
- Pathfinding actions can take up to 45 s; the controller may appear idle while the harness is `busy`.
- The bot join retries for ~30 s; if it fails, the world is likely still generating — just restart `harness.mjs`.

## Operational safety rules (learned in the field)

- **Never `git add -A` in a worktree without reading `git status` first**: working symlinks (e.g. `node_modules`) must never be committed. `.gitignore` uses `node_modules` without a slash precisely to also cover symlinks. If dependencies are needed in a worktree, use a symlink outside the repo or `NODE_PATH`.
- **Never merge or deploy to `main` while another session has uncommitted changes** or a controller is running: check `git status` and the processes first (`docker exec hermes ps aux | grep controller`).
- **Never restart or rebuild the production container while a run is active**.
- **In the base world**: never dig/break chests, tables, stations or built blocks (`DIG_PROTECTED` applies to `dig_down` and `dig_up`); prefer collecting/shearing over killing animals; never touch villagers.
- **Before claiming a file is saved or a fix is done, verify it** (`ls`, `node --test`, `/observe`): no results announced without a check.
- **Before quoting a number about a run** (duration, action count, cost), read it from a file in the same turn: `node tools/run-facts.mjs <run>`, `GET /stats` on a live harness, or `runs/<run>/{actions.jsonl,summary.json,controller.jsonl}`. A duration recalled from the conversation is not evidence — on 06/10/2026 an agent answered *"7 minutes and 17 seconds of active work"* for the diamond run and no artifact contained that figure (the run had been driven by hand over `/act`, which used to leave no ledger at all).
- **Privacy audit before every push** (`git log -p origin/main..HEAD` + grep for gamertag/xuid/keys/cache).
